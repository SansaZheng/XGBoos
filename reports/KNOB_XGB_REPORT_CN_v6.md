# 组合版 XGBoost,以及它离“每项任务都最好”还有多远 · 中文 v6

版本:CN v6(2026-11-26)。英文版见 [KNOB_XGB_REPORT_EN_v6.md](KNOB_XGB_REPORT_EN_v6.md)。[CN v5](KNOB_XGB_REPORT_CN_v5.md) 每次只改一个部件。本版把在某处有效的部件全部组合起来,由验证集逐任务选择,目标是在 Kronos_SupervisedAD 的九项任务上都拿到最好的结果。

## 结论

**组合版 XGBoost 没有在每项任务上都做到最好。** 九项中六项领先所有参照方法,一项持平(都不可用),两项落后于 Kronos_SupervisedAD 的梯度提升对照。

- **领先(6 项)**:Sapienza、SD-FMM 股票、SD-FMM 加密货币、TSTR、Elliptic、IBM AML。其中 TSTR 和 Elliptic 对梯度提升对照的领先落在自助法区间之内,更准确的说法是持平。
- **持平(1 项)**:TabFormer,0.0070 对 Kronos-mini 的 0.0074,两者都不可用。
- **落后(2 项)**:PaySim(0.970 对 0.975)和 ULB(0.762 对 0.776)。差距都小,但自助法区间都不包含零。
- **相对普通 XGBoost**,组合版在九项任务上全部更好,平均测试 AP 从 0.623 升到 0.660。
- **为补上剩余差距做的两次尝试都让结果变差。** 更宽的搜索和另一种选择规则都降低了平均值。瓶颈在验证集:多数任务的验证集只有 33–100 个异常。

这里的“最好”指本次比较里、相同划分下的最强结果:已记录的 Kronos-mini、Kronos_SupervisedAD 的 HistGradientBoosting 对照、以及 XGBoost。这些数据集上已发表的结果用的是别的划分,不能直接比较。

## 组合模型

不加正类权重。然后依次做四个选择,每一步按三个种子的平均验证 AP 决定:

1. 起始分数:按先验拟合,或 0.5。
2. 正则化:默认(深度 6)、深度 2、深度 4、`min_child_weight` 30、或 `reg_lambda` 30。
3. 新颖度特征(v5 中不用标签的“真实 / 交换”XGBoost):不用或用。
4. 种子集成:单个模型,或五个取平均。

测试标签不参与任何选择。

## 结果

测试 AP;XGBoost 各列为三个种子均值。“最强参照”取 Kronos-mini 修复版与梯度提升对照中较高者。

| SD-FMM 股票 | 0.630 | 0.443 | 0.602 | **0.664 ± 0.003** | +0.034 | 先验起点、深度 2、集成 |

### 与梯度提升对照的比较有多可靠

对测试行做配对自助法(500 次重采样,种子 42 的模型),组合版 XGBoost 减去对照:

| 任务 | 测试异常数 | AP 差 | 95% 区间 |
| --- | ---: | ---: | --- |
| IBM AML | 1,567 | +0.302 | +0.281 到 +0.321 |
| TSTR | 94 | +0.014 | −0.017 到 +0.048 |
| Elliptic | 408 | +0.003 | −0.002 到 +0.008 |
| PaySim | 4,010 | −0.008 | −0.010 到 −0.005 |
| ULB | 52 | −0.015 | −0.033 到 −0.000 |

各行独立重采样,忽略了序列内部的相关性,所以区间只可能偏窄。对照没有在 TabFormer 上跑;三项行情任务没有做自助法,那里组合版领先对照 0.012 到 0.22。

## 两次补差距的尝试,都更差

第一轮跑完后,我针对 PaySim 和 ULB 试了两种改动,都应用到全部九项任务上。

| 方案 | 改了什么 | 平均测试 AP | PaySim | ULB |
| --- | --- | ---: | ---: | ---: |
| 1. 最初的设计(上文报告的结果) | — | **0.660** | 0.970 | 0.762 |
| 2. 更宽的搜索 | 增加 15 个叶子的按叶生长树(对照所用的形式)和特征版本的选择 | 0.654 | 0.921 | 0.760 |
| 3. 合并选择 | 用方案 2 的候选,按“训练集交叉验证 + 验证集”合并打分 | 0.656 | 0.950 | 0.753 |

- **更宽的搜索反而有害。** PaySim 上验证集以 0.0025 的 AP 优势选了按叶生长树,测试上它差 0.03–0.05,而且种子间不稳定。
- **把训练集交叉验证并入选择也没有帮助。** 它提高了 SD-FMM 加密货币(0.704)和 Sapienza(0.967),降低了 PaySim、ULB、SD-FMM 股票和 TSTR。
- **把方案 1 作为结果报告,是因为它最先设计、最先运行**,而不是因为它事后得分最高。它的平均值也最高,这与“搜索越简单、对验证集的过拟合越少”是一致的。

## 为什么有两项追不上

- **PaySim**:验证集只有 33 个异常,验证 AP 在 0.75 左右而测试 AP 在 0.97 左右,验证集在这里是很差的向导。对照完全不用验证集:固定跑 100 轮。它领先 0.005。
- **ULB**:测试集只有 52 个异常,差距 0.014,区间刚好不包含零。从 v2 起试过的所有 XGBoost 变体都落在 0.75–0.77 之间。

这两项任务上,应该用梯度提升对照。

## 局限

- **这些数字偏乐观。** 搜索空间是在看过 v3–v5 的测试结果之后、在同样这九项任务上设计的。要得到干净的估计,需要没有参与设计的数据。
- **Kronos 的数字是记录值**,多数为单种子,没有重跑;SD-FMM 股票对 Kronos 的领先(0.664 对 0.630)建立在一次记录的 Kronos 运行和 6 条测试序列上。
- **TabFormer 对所有方法都不可用**:这里只有单笔交易字段;此前加入按卡历史特征的运行达到过 0.078,那里要改的是特征而不是模型。
- **IBM AML 的提升完全来自起始分数**,其机制 v5 没有查明。
- XGBoost 3.4.1;三个种子;两核 CPU 上一次只跑一个任务。

## 复现

数据准备同 v2,参数同 v4。

```bash
python -m baselines.auto_xgb    --dataset NAME [--variant V --flat FOLDER]   # 方案 1 和 2(--flat 任务不给 --variant 时为方案 2)
python -m baselines.auto_xgb_cv --dataset NAME [--variant V --flat FOLDER]   # 方案 3
python -m baselines.auto_vs_hgb --dataset NAME --flat FOLDER                 # 与对照的配对自助法
python -m baselines.auto_aggregate
```

方案 1 的结果在 `results/auto_xgb_first/`,方案 2 和自助法在 `results/auto_xgb/`,方案 3 在 `results/auto_xgb_cv/`;总表是 `results/auto_xgb/final_table.csv`。方案 1 是在加入按叶生长树之前的候选列表下跑的;要原样重跑,需从 `baselines/auto_xgb.py` 的 `REG` 中去掉 `leaves15` 并传入 `--variant`。
